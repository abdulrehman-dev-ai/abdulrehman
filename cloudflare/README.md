# Cloudflare portfolio platform

A new server-rendered Cloudflare Pages implementation alongside the existing Next.js/Vercel site. The root application is preserved for a controlled migration. Set the Cloudflare project root to **cloudflare**, never the repository root.

## Included

- Responsive portfolio, eight projects/case studies, services, contact, blog, review and policy pages.
- New case studies: Ocean Yacht Registration, Maqwi Organics (in progress), Auto Levels and WordPress migration/recovery. Earlier projects and the existing article are retained. A new engineering article starts as a draft.
- D1-backed admin dashboard at `/admin`: profile editing; project, post, service and testimonial create/edit/delete; drafts and publication; text preview; enquiries; order lifecycle; review moderation; email delivery; activity log; data export and maintenance.
- Starting prices copied from the existing repository. Server calculates request prices from published catalog entries.
- Order requests, manual bank payment verification, status emails, completed-order review invitations and moderated reviews. No card checkout or payment processor is enabled. Confirm scope and final price in writing before requesting payment. The old bank information was not imported because it has not been independently validated.
- Resend transactional outbox: order acknowledgement, admin alert, contact alerts, status updates and review invitations. Failed messages remain visible in admin.
- Password derivation, signed eight-hour sessions, secure HttpOnly cookies, same-origin writes, request size limits, input validation, IP rate limits, prepared SQL, escaped output, CSP and private admin APIs.
- System fonts and optimized WebP images; no third-party runtime scripts or review widgets.

## Local development

Requires Node 24 or newer for the SQLite-backed tests/preview; Cloudflare production uses Web APIs and D1.

```sh
cd cloudflare
npm ci
npm test
cp .dev.vars.example .dev.vars
npm run admin:password
# Put generated values in .dev.vars; choose local values for SITE_URL and ADMIN_EMAIL.
npm run db:local
npm run dev
```

The password helper prompts interactively. Store generated credentials privately and never commit them. The `.dev.vars` file and local D1 state are ignored by git. PBKDF2-SHA256 uses 100,000 iterations, matching the Workers Web Crypto limit. Put admin behind Cloudflare Access as an additional layer if desired; the application does not trust client-supplied Access identity headers.

If the environment prevents Wrangler's network-interface discovery, `node scripts/preview.js` runs the same route handlers against a fresh in-memory SQLite database. It uses `.dev.vars` when present, contains only seed/test records, and loses preview data on exit. It is a development tool, not a deployment target.

## Create the Cloudflare resources

Cloudflare sign-in remains rejected with HTTP 403 in the cloud browser. The Resend account is signed in but has no verified sending domain. No live credentials have been copied into the source. The invalid database ID in `wrangler.toml` is deliberate.

1. Authenticate with Cloudflare using your own account (`npx wrangler login`) or an appropriately scoped API token in the deployment environment.
2. Run `npx wrangler d1 create portfolio`. Replace `REPLACE_WITH_D1_DATABASE_ID` in `wrangler.toml` with the returned ID.
3. Create a Pages project connected to this repository. Root: `cloudflare`; output: `public`; no application build step is needed. The `/functions` directory is compiled by Pages. Alternatively create a direct-upload project and run `npm run deploy` from this directory. Choose Git integration or direct upload when creating the project.
4. Configure separate production and preview D1 databases. Never bind a public preview to production client data. Preview must keep orders closed and use a test email inbox. A separate Wrangler preview configuration is needed for CLI preview deployment.
5. Apply migrations once to the correct empty database with `npm run db:remote`. Never replay seed migrations against an existing installation. Back up any existing database first.
6. Configure the following settings in Pages; add credentials as encrypted secrets and redeploy.

| Setting | Purpose |
| --- | --- |
| `ADMIN_PASSWORD_SALT` | Salt generated by the password helper (secret) |
| `ADMIN_PASSWORD_HASH` | Password hash generated by the helper (secret) |
| `SESSION_SECRET` | Random secret of at least 32 characters (secret) |
| `RESEND_API_KEY` | Sending key restricted to the intended domain where supported (secret) |
| `EMAIL_FROM` | Sender on a domain verified in Resend (live mode only) |
| `EMAIL_MODE` | `disabled` by default; `test` sends only to `TEST_EMAIL`; `live` enables intended recipients |
| `TEST_EMAIL` | Your exact Resend signup inbox; required for test mode |
| `ADMIN_EMAIL` | Inbox for enquiries, order alerts and replies |
| `SITE_URL` | Exact public HTTPS origin, without trailing slash |
| `ORDERS_ENABLED` | `false` until live tests pass; then `true` |
| `DB` | D1 binding, configured in Wrangler/Pages |

`ORDERS_ENABLED` defaults to false in the checked-in configuration. For Git-based deployment, persist the intended enabled value in your production configuration and keep previews disabled; do not rely on dashboard values that Wrangler may override.

7. Keep the Vercel site live during verification. Test the Pages URL, then connect the final domain only after verification. The current Vercel subdomain cannot be moved to Cloudflare; use a custom domain or the Pages URL.

## Email and review behavior

Without a custom domain, set `EMAIL_MODE=test` and `TEST_EMAIL` to your exact Resend signup email. Test delivery uses `onboarding@resend.dev` and redirects every notification to that inbox. The outbox records `test_sent`, so a test delivery is never presented as a customer delivery. Keep public orders closed during testing. `EMAIL_MODE=disabled` makes no provider requests even if credentials exist.

For customer delivery, verify the sending domain in Resend, publish the required DNS records, configure `EMAIL_FROM`, and explicitly set `EMAIL_MODE=live`. Your free `abdulrehmansarwar.vercel.app` address can remain the website address; it is not a sending domain you control. Enquiries and orders are stored before delivery is attempted. A failed provider call cannot discard the request.

Pending emails are drained in batches of five following submissions and order updates. The admin **Retry pending emails** button provides manual retries. There is no Pages cron job in this implementation. For unattended retries, add a separate scheduled Worker calling a protected queue mechanism in a later change. Entries stop automatic retry after five failures or 23 hours, within Resend's 24-hour idempotency window. Check provider history before manually resending older entries. Customer and admin messages have stable idempotency keys. The dashboard reports API acceptance, not final inbox delivery; bounce/delivery webhooks are not implemented.

An order starts `requested`. Allowed transitions:

- requested → accepted / cancelled
- accepted → awaiting_payment / in_progress / cancelled
- awaiting_payment → paid / cancelled
- paid → in_progress / refunded
- in_progress → completed / cancelled / refunded
- completed → refunded

Marking paid/refunded requires explicit confirmation that the bank transaction was verified. Status, audit entry and notification are saved together. Completing an order sends a single-use review link valid for 30 days. The token is stored only as a hash in the order record; the email outbox necessarily contains the invitation text. Reviews remain private until moderated. No unsigned public reviews are accepted.

Fiverr: the public profile link is included. Automatic sync and iframe rendering were not verified as supported. Do not scrape Fiverr or invent reviews. Add a permitted, accurate testimonial in admin with author, rating, original source URL and the permission checkbox. No actual Fiverr review text has been imported because source evidence/permission was not supplied.

## Content management

Body content is plain text. Blank lines separate paragraphs; HTML and scripts render as text. This deliberately avoids executing user-authored MDX. Cover images accept HTTPS image URLs or existing local asset paths. Image/file uploads, rich-text formatting and a media library are not included. Drafts do not appear in the public blog, project index, detail routes or sitemap. Profile updates affect shared contact information and the homepage.

Published changes appear immediately because HTML responses are not cached. Static assets are served separately. A deployment whose DB binding is entirely absent can display the checked-in public seed content for review, but all API features fail closed. If a configured DB fails, the site returns an unavailable response instead of silently reverting published content.

## Verification before migration

- Run `npm test` and `npx wrangler pages functions build --outdir /tmp/portfolio-pages-build`.
- Check admin sign-in/sign-out, invalid credentials and blocked unauthenticated API requests.
- Publish/edit/unpublish a test article and project, then remove the tests.
- Place a test order; verify the catalog price, request persistence and both emails in Resend. Walk through permitted statuses and confirm the payment manually only for a real verified test transfer.
- Complete an order, open its review invitation, submit once, confirm a duplicate is rejected, and publish/reject it in admin.
- Submit a contact enquiry, check the private inbox and email. Check failed-email retries with a test provider configuration.
- Check all routes at phone, tablet and desktop sizes. Check keyboard navigation, mobile menu, form errors and reduced motion.
- Verify canonical URLs, sitemap, domain TLS and actual Resend delivery. Configure real payment instructions only after checking them independently.
- Confirm ordering should be opened, set `ORDERS_ENABLED=true` only in production and redeploy.

## Recovery and costs

Before database changes, export D1 (`npx wrangler d1 export portfolio --remote --output /secure/location/portfolio.sql`). Keep exports private; they contain personal data. A dashboard JSON export covers current visible records only (recent 200 orders/messages/reviews, recent 100 outbox/audit, plus all content/profile), not a full DB backup. Never commit exports.

Rollback the Pages deployment if code fails. A code rollback does not undo database migrations. Do not delete/recreate production D1 as a rollback strategy. Preserve Vercel until the new platform and domain have passed the full workflow.

Use Cloudflare Workers/D1 and Resend free plans initially, but check current quotas in each dashboard. Pages Functions consume Workers requests and D1 has separate storage/read/write limits. This is not an unlimited or guaranteed zero-cost service. No paid plan or billing change is performed by this code. No R2, paid widget or paid database is required. Run dashboard maintenance periodically to remove expired rate limits and audit events older than 90 days. Customer records are preserved until you establish an appropriate retention policy.
